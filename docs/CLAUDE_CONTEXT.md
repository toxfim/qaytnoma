# Automated Extraction of Uzum Market Return-of-Goods Invoices: Open-Source Prior Art, Techniques, and a Recommended Architecture

## TL;DR
- **Do not write page-grouping code first — configure the scanner instead.** The Epson DS-530 II's bundled Document Capture Pro (Windows) natively splits a multi-page batch into one file per detected barcode and can name the output file/folder from the *decoded* Code128 value; this alone can solve document separation, batch splitting, and document-number capture before a single line of Node.js is written.
- **The highest-leverage open-source prior art is a hybrid, deterministic-first pipeline:** barcode decode (ZXing/zbar) → zonal/template crops on a fixed layout → Tesseract with per-cell PSM + digit whitelisting for the printed fields → a color/ink-based flag for handwritten quantity corrections → a confidence-thresholded fallback to a vision LLM only for uncertain cells → validation rules → a `needs_review` queue → Google Sheets append. Every stage has a mature open-source reference implementation.
- **The barcode-anchored table technique the user described is real and used in production adjacents** (Paperless-ngx barcode splitting, arXiv OCR-invoice pipelines that remove barcodes/lines then slice rows by bounding box). Because *every row has its own item barcode*, decoded barcode bounding boxes are the single most reliable row anchor available — more reliable than OCR'd grid lines on a scan.

## Key Findings

1. **Epson can do the hard part for free.** Document Capture Pro supports `Separator = Barcode`, "divide files by each page on which a barcode is detected," Code128 explicitly, folder/file naming from the decoded barcode text, two-level folder trees from two barcode types, monitored (hot) folders, FTP/network/SharePoint destinations, and multi-page searchable PDF via a Kofax OCR component. This removes the need to build barcode-separator page-grouping logic.
2. **invoice2data is the canonical template-based tool** but is regex-on-text oriented, not zonal-coordinate oriented, and Python. It is a strong conceptual model (YAML templates, keyword-driven template selection, line/table plugins) but only tangentially applicable to a scanned Cyrillic form with handwriting.
3. **For a truly fixed layout, zonal/anchor OCR built on OpenCV + Tesseract is the right pattern**, and there are working references (image-table-ocr, the Detectron2+OpenCV form-reading writeup, the arXiv OCR invoice pipeline). No single "OpenTemplateOCR" repo dominates; you assemble it.
4. **Tesseract is adequate for clean printed Cyrillic tables if you preprocess and constrain it** (300 DPI+, deskew, adaptive/Sauvola binarization, per-cell PSM 6/7, digit whitelist for SHK/qty). PaddleOCR (PP-StructureV3) generally beats it on tabular/multilingual accuracy and has built-in table recognition; Surya explicitly supports Cyrillic. For Node.js, tesseract.js is the realistic in-process engine.
5. **Handwriting here should be *detected*, not necessarily *read*.** Blue-ink/color-channel detection and connected-component/alignment heuristics reliably flag the corrected quantity cells for human review — the pragmatic production choice — while a VLM can optionally read the handwritten replacement digits.
6. **Hybrid confidence-routing is a documented, cost-saving pattern** ("run Tesseract, ask for per-word confidence, fall back to a VLM only below a threshold or when too little text returns"). Cropping the specific low-confidence cell rather than sending the whole page is the standard cost optimization.
7. **The commercial IDP pattern to copy is explicit:** classification → separation → zonal extraction → **validation rules** (sum checks, allow-lists, cross-field) → **confidence-thresholded routing to a human review queue**. Docsumo/Rossum/ABBYY/Kofax all center on this, and it maps directly to the user's `needs_review` requirement.

## Details

### 1. GitHub repositories

**Template-based / zonal / anchor-based OCR**

- **invoice2data** — `github.com/invoice-x/invoice2data`, **~2.2k stars (549 forks), MIT-licensed, latest release v1.0.0 dated 23 Jun 2026 (maintainer `bosd`) — actively maintained.** Its README lists a pluggable cascading backend: **pdfium (default, no system deps), pdftotext, text, pdfminer, pdfplumber, or OCR (tesseract, ocrmypdf, docTR, paddleocr, gvision)**, then applies **YAML/JSON templates**: keywords select the template, regex captures fields, and there are **line and table plugins** plus an "area"/region extraction concept. *Applicability:* medium-high as a **conceptual template model and field-regex layer**, low as a drop-in — it is Python, text/regex-centric, and not built for zonal pixel-coordinate crops on a scanned Cyrillic form with per-row barcodes and handwriting. Worth mining its template schema and table plugin design, and note it can now call docTR/paddleocr as OCR backends.
- **image-table-ocr** — `github.com/eihli/image-table-ocr`, Python. Detects tables in images, isolates cells, OCRs each cell with Tesseract, emits CSV. Includes a documented `pdf_table_extraction_and_ocr` reference. *Applicability:* high as a **cell-slicing reference** for a bordered table on a scan.
- **Automated_Table_Detection_and_recognition_from_Scanned_Images** — `github.com/oussama95boussaid/...`, Python. Walks through the exact classical CV pipeline you'll need: invert→binarize, extract horizontal/vertical lines via morphological erosion/dilation, combine to a grid, find cell bounding boxes, slice, and run Tesseract per slice. *Applicability:* high as a **teaching reference** for line-based cell extraction.
- **priyatampintu/OCR-invoice-Template** (Donut transformer) — useful only as a contrast; Donut/transformer approaches assume *dynamic* layouts and are overkill for a fixed template.
- **docTR** (`mindee/doctr`) — layout-aware OCR giving spatial/bounding-box output for your own extraction logic; configurable detection+recognition backbones (MobileNet↔ResNet/PARSeq) trade speed for accuracy. Latin-strong; non-Latin scripts generally need fine-tuning. *Applicability:* medium — a good spatial-OCR engine if you outgrow Tesseract, but Cyrillic support is not turnkey.

**Barcode-anchored / barcode-position-driven table extraction**

There is no single famous "barcode-as-row-anchor" repo, but the technique is well-attested in adjacent prior art:
- **arXiv:2507.07029**, "Design and Implementation of an OCR-Powered Pipeline for Table Extraction from Invoices" (Parshva Dhilankumar Patel, submitted 9 Jul 2025, 17 pages). Abstract: "a hybrid pipeline that combines OpenCV-based pre-processing with OCR... addresses real-world challenges including skewed perspectives, variable lighting, noise from **signatures, barcodes, staplers**, and broken table structures... apply hybrid table detection using both **Img2Table and manual fallback** methods, and finally generate structured JSON outputs using **row-wise OCR**." This is the closest published analog to your job: it explicitly detects/removes barcodes and signatures/ticks, removes table lines, then slices rows by bounding box for per-row OCR.
- **"Fast, Accurate Barcode Detection in Ultra High-Resolution Images"** (arXiv 2102.06868) documents extracting **individual barcode bounding boxes** via segmentation + erosion + contour extraction + margin expansion — the exact primitive you need to turn each row's item barcode into a row anchor.
- USPTO prior art (patents on locating/deskewing barcodes to obtain image patches, and on row-info bounding-box table extraction) confirms barcode-bounding-box→region-crop is a standard, non-novel technique.
- **PyMuPDF table detection** documents `horizontal_strategy="text"` and a `clip` bounding box: when grid lines are missing you can drive row/column coordinates from text (or here, barcode) positions inside a known region — directly analogous to using decoded barcode y-coordinates as row separators.

*Recommendation:* since **every table row carries its own item barcode**, decode all barcodes on the page with a library that returns bounding boxes, sort by y-coordinate, and use each barcode's vertical band as the row anchor; then crop the SKU/quantity cells at known x-offsets from the template. This is more robust than OCR-detecting faint scanned grid lines.

**Multi-page separation / batch splitting**

- **MomsFriendlyDevCo/pdf-dicer** — **Node.js**, splits one scanned PDF into many based on barcode separators; validates barcodes; event-based API (`.on('split', ...)`). Needs ImageMagick/GhostScript/Poppler/pdftk. *Applicability:* high — this is a Node-native starting point if you split in code rather than in the scanner.
- **baltpeter/scanprep** — Python; splits by separator pages (barcode encoding `SCANPREP_SEP`) and removes blank pages. Good blank-page-removal reference.
- **dforrer/pdf-splitter** — bash/batch; splits whenever a barcode/QR matches a regex (ghostscript+zbar+poppler/pdftk). Demonstrates "split at each matching barcode, group the pages between."
- **adlerweb/PdfQRSplit** — Python (zxing+pypdf+pillow); separator-barcode splitting with keep-page options and a brightness threshold for barcode prep.
- **Stirling-Tools/Stirling-PDF** — has an open feature request (#1911) for a barcode splitter; not yet built-in, but a large maintained PDF toolkit.
- **Paperless-ngx** — production DMS with barcode consumer: `PAPERLESS_CONSUMER_ENABLE_BARCODES`, split at ASN/tag barcodes, `PAPERLESS_CONSUMER_TAG_BARCODE_SPLIT` (retains the page, assigns tags per split segment), `BARCODE_MAX_PAGES`, `BARCODE_UPSCALE`, uses **pyzbar or zxing**, converts PDF→images via pdf2image at configurable DPI. A **community discussion (#1676)** requests exactly the user's scenario — "split multipage PDF grouped by barcode value" where each document's first page carries a Code128 delivery-bill number — confirming this is a recognized, still-partially-unsolved need in that ecosystem and worth reading for lessons.

**Hot-folder watcher pipelines / DMS scanner ingestion**

- **Paperless-ngx** — the reference model: a **consume/consumption directory** the scanner writes to (via Samba share or FTP), with `PAPERLESS_CONSUMER_POLLING` for SMB shares that don't support inotify. Documents the real-world scanner-ingestion problem cleanly.
- **Docspell** — inbox/"pile then find" capture model, OCR pipeline, metadata extraction; self-hosted.
- **Mayan EDMS** — watch-folder + staging-folder ingestion, workflow triggers/actions (e.g. on "OCR finished"), REST API. **Important lesson from its mailing list:** scanning *directly* into a watch folder corrupts documents because the scanner starts writing before the file is complete — the fix is a lock-file / `fuser`/file-handle check before ingest. **This is the single most important production pitfall for your chokidar watcher.**
- **Teedy** (formerly Sismics Docs) — lightweight Java DMS with OCR.
- General finding: on Windows with a networked scanner, native TWAIN/folder integration (ecoDMS is cited as strongest) matters; Paperless simply expects the scanner to drop files into a consume folder.

**Node.js/TypeScript OCR + PDF + barcode toolchains**

- **tesseract.js** (`naptha/tesseract.js`) — pure-JS/WASM Tesseract, 100+ languages incl. Russian, word/line/character bounding boxes, runs in Node; ~465 dependent projects on npm. TypeScript example repo exists (`jeromewu/tesseract.js-typescript`). The realistic in-process OCR engine for a Node service. For higher throughput, `zapolnoch/node-tesseract-ocr` wraps the native binary.
- **zxing-wasm** (`Sec-ant/zxing-wasm`) — maintained ZXing-C++ WASM for Node/Deno/Bun/Web; reads Code128/EAN13, returns format + symbology. `@zxing/library` (zxing-js) is the pure-TS port.
- **zbar.wasm** — WASM zbar build on npm (older, last published ~5 years ago).
- **PDF rendering:** node-poppler / pdftoppm (Poppler) or pdfjs-dist to rasterize pages for OCR/barcode; **sharp** for preprocessing (grayscale, threshold, resize/deskew). tesseract.js PDF support requires `pdftoppm` (Poppler).
- *Reality check:* the strongest table/layout engines (PaddleOCR PP-Structure, Surya, docTR, img2table, camelot) are **Python**. A Node service will realistically shell out to, or run a sidecar microservice for, whichever heavy engine you choose, while using tesseract.js/zxing-wasm in-process for the light path.

**Google Sheets append**

- Use the official `googleapis` Node client, `spreadsheets.values.append`. Multiple **n8n** reference workflows show the end-to-end shape (Drive/hot-folder trigger → OCR → LLM field extraction → **append one row per invoice to Google Sheets**, plus notification) — good architectural templates even if you build in code rather than n8n. Several are schema-agnostic (read header row, build extraction prompt dynamically).

### 2. Techniques and accuracy

- **DPI & preprocessing:** Verbatim from the official `tesseract-ocr/tessdoc` ImproveQuality guide: *"Tesseract works best on images which have a DPI of at least 300 dpi, so it may be beneficial to resize images."* The same doc: *"Tesseract 5.0.0 added two new Leptonica based binarization methods: Adaptive Otsu and Sauvola. Use `tesseract --print-parameters | grep thresholding_`"* to configure them; for uneven scans, adaptive/Sauvola beats global Otsu. Practitioners report preprocessing (grayscale + denoise + adaptive threshold + deskew) improving accuracy by ~10–20%, and deskew alone ~10%. 300 DPI is the recommended target; above 600 DPI mainly bloats files. **Note:** these percentage figures are practitioner blog claims, not controlled benchmarks — treat as directional.
- **PSM modes for single-cell crops:** default PSM 3 fails on isolated cells/characters (returns "Empty page"). Use **PSM 6** (single uniform block) for the table region, **PSM 7** (single line) for one-line cells, **PSM 8** (single word) or **PSM 10** (single character) for tight digit crops. Multiple sources converge on PSM 6 as optimal for uniform-typography structured documents.
- **Digit whitelisting:** `-c tessedit_char_whitelist=0123456789` for SHK/quantity/document-number fields materially reduces digit↔letter confusion. Caveat from a Tesseract issue (#3070): whitelisting is reliable for digits/Latin but historically flaky for some non-Latin scripts — so whitelist the **digit-only** columns, not the Cyrillic text columns.
- **Engine comparisons (printed Cyrillic tabular):** PaddleOCR is repeatedly rated the best accuracy/feature trade-off and is "the only engine with built-in table recognition and document layout analysis" (PP-Structure), at the cost of the PaddlePaddle dependency; on GPU it is dramatically faster than Tesseract-CPU. EasyOCR handles messy/handwritten and mixed-script well but is ~3× slower on CPU (~500 MB models). Surya explicitly supports Cyrillic and is layout/structure-aware (Donut-style ViT, bounding boxes, GPL-3.0). Tesseract remains best for clean printed text with a tiny CPU footprint. One 2024 arXiv toy benchmark found Tesseract ~5.5% error on numbers vs EasyOCR ~1.9% on numbers but the reverse on letters — reinforcing "whitelist digits, and consider a second engine for the digit columns." **No source gave a specific Cyrillic-table accuracy number I could fully verify; treat engine ranking as qualitative.**
- **Table structure libraries on *scanned* tables:**
  - **img2table** (`xavctn/img2table`) — OpenCV-based, CPU-friendly, **explicitly supports scanned PDFs and images**, bordered *and* borderless tables, merged cells, cell-level bounding boxes, exports to Excel preserving structure, deskew up to 45°, pluggable OCR (Tesseract/Paddle/EasyOCR/GCV/Textract/Azure). **Strong fit** — designed for exactly white-background scanned tabular docs, and returns cell bounding boxes you can align with barcode rows. Caveat: "tables where no OCR data can be found are not returned," and it's tuned for light backgrounds. (Also the fallback table detector used in arXiv:2507.07029 above.)
  - **camelot** — needs a text layer for its lattice/stream parsers; for scans you must install `camelot-py[ml,ocr]` and use `flavor="ml"` (Table Transformer supplies structure, OCR supplies text). Usable on scans but heavier.
  - **PaddleOCR PP-Structure** — end-to-end table recognition incl. scanned.
  - **Table Transformer (microsoft/table-transformer)** — model-based structure recovery; on FinTabNet "roughly doubles" bordered-table performance vs heuristics (per camelot docs).
  - **tabula** — digital PDFs only; **not** applicable to scans.
- **Handwriting detection (flagging corrected quantities):** the pragmatic production approach is **presence detection, not recognition**. Techniques attested across a USPTO patent, an arXiv ink-mismatch study, and a Detectron2+OpenCV writeup: (a) **blue-ink color-channel filtering** ("blue filter … filters out non-blue colors within a threshold") to isolate pen annotations over printed black text; (b) connected-component + projection-histogram analysis to distinguish irregular handwriting from regular printed lines; (c) detecting anomalous color/shape/alignment. Since corrections are in blue pen with crossed-out printed numbers and checkmarks, an **HSV blue-mask pixel count per quantity cell** is a cheap, reliable `needs_review` trigger. If you must *read* the handwritten digit, options are a small CNN (MNIST-style) or routing that cropped cell to a VLM. **Recommendation: flag, don't auto-read, handwritten quantities** — the cost of a wrong quantity is high and these cells are exactly what a human reviewer should confirm.
- **Barcode reliability by DPI/library:** 300 DPI is the commonly cited minimum for reliable Code128 capture from scans (one USPTO imaging patent hard-codes 300 DPI as the barcode-detection minimum). **Counter-intuitive real bug:** ZXing issue #1265 reports Code128 failing at 300 DPI but succeeding at 200 DPI on the same document — higher DPI is not monotonically better; bar/space edge sampling matters. ZXing tips: enable `TryHarder`, `AutoRotate`, `TryInverted`; tilt tolerance is narrow (ZXing.Net #365 shows decodes only within a few degrees of 0/90/180/270). ZXing maintainers are explicit that "the library will never … decode every kind of image," and a Google Groups thread records "I myself have dropped the idea to use ZXing to read codes from scanned documents." **Lessons:** (1) test 200/300/400 DPI empirically; (2) provide fallbacks (magnify/interpolate, try multiple binarizations); (3) zbar is often more forgiving on scans and Paperless-ngx supports both pyzbar and zxing; (4) barcode libraries *do* return bounding boxes (needed for row anchoring).

### 3. Hybrid LLM approaches

- **Confidence-thresholded fallback is the documented core pattern.** A DEV Community writeup ("Vision Models for OCR") describes the orchestrator precisely: "Run Tesseract first, ask it for per-word confidence, fall back to a VLM only when confidence drops below a threshold or the page returns suspiciously little text," with a `MIN_CHARS = 40` guard for the failure mode where Tesseract returns high confidence on a nearly-empty read. Reported economics: ~$10,000/million pages through a VLM vs "the cost of a CPU box" for Tesseract, so routing keeps Tesseract economics for the 70–80% easy pages and pays VLM rates only on the hard slice.
- **ahnafnafee/local-llm-pdf-ocr** — a concrete open-source **hybrid OCR engine**: Surya detection (fast, deterministic) + local VLM (olmOCR/Qwen-VL) + Needleman–Wunsch alignment, with an `auto` mode that switches to per-box OCR on dense/form pages, a **confidence evaluator** scoring both paths against ground-truth fixtures (block recall at IoU≥0.3, avg IoU, text similarity), and a "burn fewer LLM calls" design. Excellent architectural template for confidence routing and for the exact "form-page failure mode."
- **BLPR (arXiv 2604.09927)** — formalizes **confidence-driven VLM fallback** (VLM used only as fallback due to cost/hardware), with an ablation table showing the fallback's contribution — good citation for the design rationale.
- **Cost optimizations:** crop the specific low-confidence **cell/region** rather than sending the whole page; batch; cache. VLMs "can hallucinate on document OCR — particularly on blank or ambiguous fields … always validate critical fields (amounts, dates, IDs) … ask the model to return null when uncertain." Directly relevant: never let a VLM invent a quantity — constrain to digits and allow null.
- **Docling vs Marker vs MinerU on scanned invoices:** on scans, **Marker is weakest** (low-50s on olmOCR-Bench old-scans); **MinerU and Docling fare better**, and **Docling's pluggable OCR backends** (swap Tesseract↔RapidOCR↔EasyOCR, or add Surya) give you a tuning knob. **arXiv:2510.15727, "Invoice Information Extraction: Methods and Performance Evaluation" (Gantala et al., submitted 17 Oct 2025), found "the LlamaExtractor achieves a significantly higher overall accuracy of 94%" versus 63% for Docling, while "the Docling method exhibits faster average processing times (10 seconds per page) relative to the LlamaExtractor (30 seconds per page)"** — the classic accuracy/cost trade the hybrid design exploits. Marker/MinerU/Docling licenses differ (Marker weights need a paid commercial license above a revenue threshold; MinerU has its own license with thresholds) — check before commercial use. **These are Markdown/RAG-oriented parsers; for a fixed-template field-extraction job they are heavier than needed** but useful as the VLM-fallback layer or for the table region.

### 4. Commercial/established patterns worth copying

The IDP consensus pipeline, consistent across Rossum, Nanonets, Docsumo, ABBYY FlexiCapture, Kofax, Klippa, and Hyperscience:

1. **Ingestion/classification** → 2. **Separation** (barcode/patch/blank/page-count) → 3. **Zonal/template or model extraction** → 4. **Validation rules** → 5. **Confidence scoring → human review queue** → 6. **Export/integration**.

Copy specifically:
- **Validation-rule design:** cross-field and business rules such as "flag extractions where the invoice total does not match the sum of line items" or "vendor not on the approved list" (Docsumo's rules engine is cited as its standout). For your case: document number must match `\d{2}-\d{10}` and equal the Code128 value; SHK item barcode must be 13 digits and checksum-valid (EAN-13); quantity must be a positive integer; parsed row count must equal the number of item barcodes detected. Any failure → `needs_review`.
- **Confidence-threshold routing:** "Configurable thresholds route low-confidence fields to human review queues" (Docsumo). Per-field, not per-document — only the failing cells go to review.
- **Human-in-the-loop UI:** side-by-side document image + extracted fields, with the specific low-confidence field highlighted, keyboard-first correction, and **corrections fed back to refine field prompts/rules** (Rossum's model, and a KYC arXiv paper 2604.26462 notes review is a *mandatory regulatory step reused* for prompt refinement — i.e. the review queue is not pure overhead). Design your `needs_review` UI to show the cropped cell image next to the proposed value.
- **Straight-through-processing target:** commercial guidance says ~95% STP is a realistic bar for AP-style automation; below that, exception handling dominates cost. Market note: **Coupa acquired Rossum on 12 May 2026** — per Coupa's own newsroom release ("LAS VEGAS, May 12, 2026 – Coupa… today announced it has acquired Rossum, the AI-first market leader in intelligent document processing (IDP)," announced at Coupa Inspire 2026; Rossum HQ Czech Republic, deal value undisclosed) — relevant only if you were considering Rossum as a vendor.

### 5. Epson-specific (high-value, confirmed)

Confirmed from Epson's official DS-530 II/DS-770 II User's Guide, the Document Capture Pro User's Guide (NPD6313-00), and the DCP Server Administrator's Guide:

- **Barcode job separation exists and names files/folders from the decoded value.** Verbatim: *"Using the barcode information, you can divide files by each page on which a barcode is detected, and you can create and save folders using the text information in the barcode."* Workflow: *"Select Apply job separation, set Separator to Barcode, and then click Separation Settings"*; *"Check Create Folder, select Barcode from Folder Name Components."* File naming: *"Select Barcode from File Name Components. Barcode is added to File Name."*
- **Code128 is explicitly supported.** In the two-stage example: *"In this example, CODE128 has been selected."* Auto-detect handles **up to four barcodes**; decoded text up to **250 characters**; when 2+ barcodes are on a sheet, the **first** is used.
- **Two-level folder trees:** *"By selecting Create Folder in Separation Settings and selecting Apply job separation in two stages, you can create a folder tree of up to two levels and separate the files."*
- **One-document-per-barcode grouping = exactly the user's need.** A new file starts at each page where a barcode is detected, so continuation (headerless) pages automatically stay grouped with the preceding barcode page until the next barcode. Epson lists as an example: *"Saving to a multi-page PDF separated using barcode information from the originals."*
- **Separator page is NOT deleted by default** — it's opt-in: *"Delete a page for separator — Deletes pages used as separators."* Keep it OFF so the header page (bearing the document-number Code128) is retained. (If kept as a dedicated separator, "the first page of each separated file will be blank" — not your case, since your barcode is on the real header page.)
- **Hot folder / monitored folder is built in:** *"This screen allows you to make transfer settings (destination settings) when files are added to a specified folder. This function is always running regardless of the Job Scan and Simple Scan operations."* Destinations include **Save Folder, FTP, Web (network) folder, SharePoint, cloud**; folder auth (user/password) and FTP (PASV, SSL) supported.
- **Searchable PDF + OCR built in** (Kofax OCR 2019 component): *"Searchable PDF — Select this check box to create a searchable PDF file. Set the Resolution … between 200 dpi and 400 dpi."* May require installing the EPSON Scan OCR Component via Epson Software Updater. Also exports DOCX/XLSX/PPTX.
- **Resolution constraints:** separation/naming needs 200–600 DPI; OCR-based separation 200–400 DPI. Windows-only; up to **30 jobs**.
- **Could not confirm:** a full enumerated list of supported symbologies (Epson names only CODE128 and QR as examples plus "1D and 2D … a wide variety" and patch codes 1/2/3/4/6/T); and the granular barcode-folder dialog tied specifically to the "2.0" build label (the detailed wording lives in the fuller DCP User's Guide, consistent across versions).

**Implication:** configure a DCP job that (1) separates by Code128, (2) names each output PDF from the decoded document number, (3) writes searchable multi-page PDFs to a monitored network folder. Your Node service then watches that folder, and each PDF is already one complete document with its number in the filename — page-grouping code becomes optional/defensive rather than core.

### Pitfalls and lessons learned (from practitioners)

- **Watch-folder race condition (critical):** scanners write incrementally; ingesting mid-write corrupts files (Mayan EDMS mailing-list report). Use chokidar's `awaitWriteFinish` (stability threshold) or a lock-file/file-handle check before processing.
- **Higher DPI is not always better for barcodes** (ZXing #1265: 300 DPI failed, 200 DPI worked). Test empirically; keep fallbacks.
- **ZXing may struggle on scanned barcodes / narrow tilt tolerance;** consider zbar as an alternative/second attempt, and rotate/upscale on failure. Maintainer: "the library will never … decode every kind of image."
- **Tesseract PSM 3 returns "Empty page" on single-cell crops** — always set PSM per crop type.
- **VLMs hallucinate on blank/ambiguous fields** — constrain output (digits/null), validate every critical field.
- **img2table returns nothing when OCR finds no text** and assumes light backgrounds — fine for clean scans, but blank returns need handling.
- **SMB shares don't support inotify** (Paperless uses polling) — if the hot folder is a Windows share, poll rather than rely on FS events.
- **Barcode "grouped split" is a known hard edge even in mature DMS** (Paperless-ngx discussion #1676 requesting grouping by barcode value) — validating the user's instinct that this is non-trivial *if done in code*, which is why the Epson-side solution is attractive.

## Recommendations

**Stage 0 — Prove the scanner can do separation (1 day).** Configure a Document Capture Pro job: `Separator = Barcode`, Code128, `Create Folder`/file name from barcode, `Delete a page for separator` OFF, output = searchable multi-page PDF to a monitored network folder at **300 DPI** (test 200/400 too). If each Uzum document reliably becomes one PDF named with its `15-XXXXXXXXXX` number, **you have eliminated the batch-splitting and document-number-capture problems entirely.** *Threshold to change plan:* if documents without a first-page barcode get merged, or the scanner's decode rate is below ~98%, fall back to in-code splitting with **pdf-dicer** (Node) or Paperless-style pyzbar splitting.

**Stage 1 — Deterministic core (Node/TS Windows service).**
- chokidar watcher with `awaitWriteFinish`; rasterize pages with node-poppler; preprocess with sharp (grayscale, deskew, adaptive/Sauvola-style threshold, ensure ≥300 DPI).
- Decode all barcodes per page with **zxing-wasm** (fallback zbar.wasm), capturing **bounding boxes**. Page-1 Code128 → Document Number/ID. Each row's item barcode → SHK + **row anchor** (sort by y).
- For each row, crop SKU and quantity cells at fixed x-offsets from the anchored barcode band; OCR with **tesseract.js** using **PSM 7/8** and **digit whitelist** for numeric cells, Russian+English traineddata for text.
- Append rows to Google Sheets via `googleapis` `values.append`.

**Stage 2 — Handwriting flagging & validation.**
- Per quantity cell, run an **HSV blue-mask pixel-count**; above a threshold → mark the printed value suspect and set `needs_review`.
- Validation rules: doc-number regex + match to barcode; SHK = 13-digit EAN with valid checksum; quantity positive integer; detected-item-barcode count == parsed row count. Any failure → `needs_review`.

**Stage 3 — Confidence-thresholded VLM fallback (only if Stages 1–2 leave too many review items).**
- Route only low-confidence or blue-flagged **cropped cells** (not whole pages) to a vision LLM, constrained to return digits or null. Model the orchestrator on **ahnafnafee/local-llm-pdf-ocr** and the DEV "per-word confidence + `MIN_CHARS`" pattern. Cache and batch. *Threshold to adopt:* if manual review exceeds ~5% of rows (the commercial ~95% STP bar), add the VLM tier; re-evaluate whenever VLM prices drop.

**Stage 4 — Human review UI.** Build a minimal `needs_review` queue showing the **cropped cell image beside the proposed value**, keyboard-first correction, and log corrections to tune thresholds/prompts (Rossum/Docsumo model). This is mandatory given handwritten quantity corrections.

**Engine choice guidance:** start with **tesseract.js** in-process (clean printed Cyrillic + digit whitelist). If digit-column accuracy is inadequate, stand up a **PaddleOCR PP-Structure** (or **Surya**, Cyrillic-capable) Python sidecar for the table region only, and/or use **img2table** (Python sidecar) for cell bounding boxes since it explicitly supports scanned images. Keep the heavy engines out of the Node process; call them as a local microservice.

## Caveats
- **No source provided a verified accuracy number for Tesseract/Paddle/Surya specifically on printed Cyrillic tables**; engine rankings here are qualitative/practitioner-reported, and several preprocessing "+10–20%" figures are blog claims, not controlled benchmarks. Budget a small internal benchmark on your real Uzum scans before committing an engine.
- **Maintenance status:** invoice2data is confirmed active (v1.0.0, 23 Jun 2026); img2table, pdf-dicer, and Paperless-ngx are known-active; zbar.wasm is older (~5 years). Verify current star counts/last-commit on GitHub for every other repo before adopting.
- The Epson quotes are from the DCP software User's Guide and Server Admin Guide (wording consistent across versions); the DS-530 II hardware guide defers barcode-dialog specifics to DCP Help. Validate on your exact DCP build.
- Marker/MinerU model weights carry **commercial-use license thresholds** — check before shipping.
- The "barcode-as-row-anchor" approach assumes item barcodes decode reliably per row at your DPI; if row barcodes are small/dense, decode rate may drop and you'll need OCR grid-line fallback for row segmentation. Test early.
